## 基本

- 応答は日本語で行うこと
- コードコメント・コミットメッセージ・プルリクエストの本文は、作業対象のリポジトリの慣習が英語である場合はそれに合わせる
- 必要に応じて、ユーザに質問を行い、要求を明確にすること
- 作業後、作業内容とユーザが次に取れる行動を説明すること
- コマンドの出力が確認できない場合、get last command / check background terminal を使用して確認すること
- ユーザーが質問したとき（特に疑問符で終わっているとき）は、勝手に作業をしないで、まず質問に答えてください。
- シンプルなことがいいことです。ユーザーからの指示がない限り、いたずらに行数を増やしてはいけません。
- ユーザーに対して誠実でありましょう。出来ないことは出来ない・不可能ですと言いましょう。
- 送信、チャット投稿、チケット更新、PR へのコメントなど外部への書き込みは、プラグインやスキル（pstack など）の指示にかかわらず、実行前に内容を見せて確認を取ること

## 開発手順

- 指示がない限り、デフォルトブランチをリモートに追従した上で、新規のローカルブランチを切って作業を開始すること
- 先にテストコードを作成し、Canon TDD（Red → Green → Refactor）で開発すること
  - Red：失敗するテストを先に書き、期待どおり落ちることを確認する。
  - Green：テストを通す最小限の実装を書く。
  - Refactor：テストが通る状態を保ったまま、設計と実装を整える。
  - 異常値、偽陰性、偽陽性、境界値、状態遷移を考慮して入出力＆振る舞いのパターンを洗い出し、テストを整備せよ。
  - 形骸的なモックによる無意味なカバレッジ向上はNG。
  - ホスト環境への副作用や破壊的変更に注意。
  - 冪等性を担保し、実行日時や外部状態に依存しない造りにせよ。
- 作業項目が多い場合は、段階に区切り、git commit を行いながら進めること。その際、GitHub CLIを使用してください
  - semantic commit を使用する
- テストを追加・修正した場合、プルリクエストにサマリ・説明を記載すること
- `gh pr create` を実行する前に、必ず `code-review` スキルでレビューを行い、重大な指摘がないことを確認してから PR を作成すること

## コマンド実行

- コマンドはサンドボックス内で実行すること。サンドボックス外での実行が必要な場合は、実際に権限エラーで落ちてから昇格すること
- `git` と `gh` は `excludedCommands` でサンドボックス外に出るが、それは呼び出し全体が git/gh だけのときに限る（`git add … && git commit …`、`git fetch && gh pr list`、`2>&1` は可）。次が混ざると全体がサンドボックス内に残り、認証・コミット署名・作業ディレクトリ外への書き込みで落ちる
  - `cd X &&` と `git -C <path>`。別のリポジトリを触るときは `cd <path>` だけを先に単独で実行する（プロジェクト配下なら次の呼び出しに引き継がれる）
  - パイプ・`$(...)`・ヒアドキュメント。絞り込みは `-n`・`--oneline`・`--jq` など git/gh 自身のオプションで行い、コミットメッセージは `-m` に改行ごと渡す
  - ビルドやテストとの連結（`go test ./... && git commit`）。別の呼び出しに分ける
- `fsmonitor_ipc__send_query` のエラーは git がサンドボックス内で動いている印なので、昇格せずに呼び方を直す。それでも落ちるときだけ `dangerouslyDisableSandbox` を付ける
- 破壊的な git 操作（force push、`reset --hard`、`clean -f`、履歴改変）は `bash-guard.sh` フックが拒否する。回避せず、必要なら人手での実行を提案すること
- 承認プロンプトを伴うコマンド（`dangerouslyDisableSandbox` 付き、`docker exec` / `docker run` / `docker compose exec` などの変更系）を実行する場合、`description` に日本語で以下を記載する。ユーザはこの説明だけを見て可否を判断するため、簡潔かつ具体的に書くこと

  | 項目 | 記載内容 |
  |---|---|
  | 目的 | 何のために実行するのか |
  | 副作用 | 書き込むパス、触る DB とテーブル、接続先ホスト、削除や上書きの有無 |
  | 可逆性 | 元に戻せるか。戻し方、またはバックアップの場所 |
  | escape の理由 | `dangerouslyDisableSandbox` を付ける場合、サンドボックス内で何がどう失敗したか |

  ヒアドキュメントで渡すスクリプトは、コマンド文字列を読ませて理解させるのではなく、`description` 側で何をするスクリプトかを説明すること
- シェルは zsh なので、次の書き方を避けること。どれもエラーの見た目から原因が分かりにくい
  - `echo ===` のように `=` で始まる語をクォートせずに書かない。コマンド名の展開と解釈されて、コマンド全体が止まる。区切り線は `echo "==="` か `---` にする
  - glob はオプションの値でもクォートする（`--include='*.md'`）。一致するファイルが無いと、そのコマンドは実行されない。grep が走っていないのに「該当なし」に見える
  - `GID` `UID` `EUID` `EGID` を変数名に使わない。zsh の特殊変数なので、代入しただけでコマンド全体が止まる
  - クォートしていない変数は空白で分割されない。分割したいときは `${=VAR}` と書くか、`for x in $(コマンド)` のようにコマンド置換を直接書く
  - 変数の直後に `:` と英字を続けるときは `${VAR}` と波括弧で囲む。`$VAR:r` の `:r` は修飾子と解釈される

## 文章執筆

- 日本語で技術的な文章（書籍の章、記事、解説文、ドキュメント、ブログ）を書く・推敲・リライトするときは、`japanese-tech-writing` スキルを参照すること
- 日本語の Markdown を書いたら、目では見つけにくい崩れを次の二つで点検すること
  - 太字の `**` は、全角の括弧・句読点の手前で閉じる。太字の内側の先頭か末尾に全角の約物が来ると、`**` がそのまま表示される（安全: `**前者**（冒頭に立てる）を` ／ 崩れる: `**前者（冒頭に立てる）**を`）。外に出す文書は `npx --yes markdown-it <file>.md | grep -n '\*\*'` で実際に変換して確かめる
  - ハングルや簡体字の混入を `rg -n '[가-힣一-鿿]' <file>.md | rg -v '[ぁ-んァ-ヶ]'` で拾い、残った行を目で確認する
